# bugs
bugs that frequently keep recurring after code is modified. add comprehensive tests for all these bugs to avoid regression. when a new bug is found, update this file with a brief description.

1. scratch layer bugs
1.1 conflict between scratch layer and a always-on-top window: scratch layer despite being over the window fails to get focus
1.1 opening a app associated with scratch layer fails to open or window open delayed by 2-3 seconds
   1.1.1 root cause (live repro: GNOME Shell 50.1/Wayland, `sync-taskbar-order=true`, Vicinae with a `scratch_layer` winprop): the scratch entry paths (`scratch.js makeScratch()`, `insertWindow()`'s scratch/sticky branches) called `forceTaskbarResync()`, which ran *synchronously* on the `first-frame` stack and unconditionally emitted `AppFavorites 'changed'`. That signal runs every listener synchronously — GNOME Shell's `AppDisplay._redisplay()`, not just DTP (whose listener is deferred) — producing measured main-thread blocks of ~1.5–1.7 s starting ~40 ms after the window was mapped (RTT sampler on `org.gnome.Shell.Introspect`). Disabling Dash-to-Panel did not remove the block; `sync-taskbar-order=false` did. Tiled opens showed only a shorter (~0.5 s) block later in the open, not in the mapping path — which is why only scratch opens were reported.
   1.1.2 fix (`eeba63d` scheduler + follow-up): the *forced* nudge is gone from the never-tiled entry paths — `scratch.js makeScratch()` and `insertWindow()`'s scratch/sticky branches call `scheduleTaskbarSync()` (signature-gated). A scratch window that never joins a Space leaves the stamped order unchanged, so no nudge happens at all; toggling a tiled window to scratch still nudges once (the order signature changes when it leaves its Space). Forced passes remain only for the login startup cover (§3.2) and explicit `forceTaskbarResync()` callers. Additionally the nudge targets Dash-to-Panel directly (`taskbar.js createDashToPanelNudge()` → each panel's `Taskbar._queueRedisplay()`, DTP's own deferred path) instead of emitting global `AppFavorites 'changed'`; without DTP it is a no-op (only DTP consumes `_dtpPosition`).
   1.1.3 regression tests: plain gjs — `tests/taskbar.test.js` ('Dash-to-Panel nudge — target selection', 'regression: scratch-window open stays gated'); shell session — `tests/scratch.test.js` (entry path runs, no forced pass queued via `getTaskbarSyncState()`) and `tests/tiling-taskbar.test.js` (live nudge accessor + snapshot wiring).

3. dash to panel extension
3.1 order of windows is different: dash to panel groups app windows together unlike paperwm which follows its own rule (current setting: open new window to end)
3.2 on startup bug: when some apps are scheduled to open on startup, app icons are missing in dash to panel though windows do open. this happens only during startup otherwise icons are visible as expected. e.g., if three windows open (brave1, obsidian, brave2), obsidian icon is not visible. or if obsidian is visible then brave1 and brave2 icons are missing. 
   3.2.1 root cause: taskbar order was stamped + nudged synchronously from `Space.layout()`/`window-created` during the autostart burst; the nudge could reach DTP before DTP itself finished enabling (or after it painted an early snapshot), and the signature gate then suppressed any later nudge because the order had not changed since. Result: an icon (or two) stays missing until the next order change. A first attempt at a fix (commit `602a0b9`) was reverted in `90fcd31` for breaking `tiling.js` (stray tokens + unrelated edits).
   3.2.2 fix (`eeba63d`): taskbar logic moved to `taskbar.js`, a dependency-injected scheduler — every pass is debounced (50 ms) + idle-deferred (no synchronous work in layout/signal handlers), nudges are signature-gated, and during login the shell `enable()` starts a bounded "startup phase" that arms forced re-assert chains (1 s / 3 s / 8 s, phase capped at 30 s) so a late- or slow-to-enable DTP converges. `disable()` disposes the scheduler and clears ranks. See `taskbar.js` header.
   3.2.3 regression tests: `tests/taskbar.test.js` (62 cases, fake clock, incl. the exact login-burst scenarios: late-enabled panel converges; single-app order unchanged still re-asserted; mid-session enable gets no startup chain). Wiring smoke tests: `tests/tiling-taskbar.test.js`. Required DTP dconf settings are documented in `CHANGES-paperwm-mod.md` §9.
   3.2.4 follow-up (part of the §1.1 fix, `CHANGES-paperwm-mod.md` §15): the re-sort nudge now goes through `createDashToPanelNudge()` (DTP's own deferred `Taskbar._queueRedisplay()`) instead of a global `AppFavorites 'changed'` emit; the forced re-assert chain semantics are unchanged and the §3.2 regression scenarios still pass.
3.3 span mode ignores per-monitor panel/top-bar insets: with Dash-to-Panel at the top or bottom of the primary monitor (and the stock GNOME top bar when kept), tiled windows overlapped the panel. `computeSpannedWorkArea()` unioned every monitor's work area, so a secondary monitor without a panel reached the full screen edge and discarded the primary's top/bottom inset (`getWorkAreaForMonitor()` was correct). Fix (`CHANGES-paperwm-mod.md` §17): union work areas horizontally but intersect their vertical bands (`top = max(wa.y)`, `bottom = min(wa.y + wa.height)`), falling back to the union for vertically stacked monitors with no common band. Trade-off: the panel-height band is also kept free on unobstructed monitors because all columns share one vertical band. Regression tests: plain gjs `tests/lib.test.js` (`Lib.computeSpanWorkArea`: top/bottom panel, GNOME top bar + bottom panel, mixed heights, vertical fallback, missing work area, zero-height clamp) and shell-session `tests/tiling-span.test.js` (live accessor integration with mocked monitors/work areas).

3.4 `gnome-extensions install --force` destroys the symlinked dev install (reported 2026-11-06): with the extension installed via `make install` (a symlink to the repo), running `make release && gnome-extensions install --force paperwm-mod@paperwm.github.com.zip` emptied the symlink target. `gnome-extensions` 50.1 follows the symlink, deletes the target's contents — including `.git` — and then aborts with `Can't recursively copy directory`. The repo lost `metadata.json`, `extension.js`, `app.js`, `imports.js`, `lib.js`, `schemas/`, and most upstream files; the running shell failed at 12:31 with `Could not load extension ... Missing metadata.json`, so tiling and Super+J/K stopped working. The command chain's `&&` stopped at the failed install, so the later disable/enable never ran.
   3.4.1 recovery: restore missing files from `https://github.com/0king/paperwm-mod` (`durjan/paperwm-mod`) with `rsync --ignore-existing`, copy the clone's `.git`, set `git config core.filemode false` (the NTFS mount reports all files as 0777), and re-apply local working-tree edits. `make test` then passes 117/117.
   3.4.2 prevention: never run `gnome-extensions install --force` against a symlinked dev install. `make release` only builds the zip; install that zip in a GNOME Shell VM or on a machine with a real (non-symlink) extension directory. For local development use `make install` and restart the shell (logout/login on Wayland). GNOME Shell 50 does not rescan extensions mid-session, so a failed load stays cached until logout/login.

4. settings / schema

4.1 `GSettings key remember-window-sizes not found in schema org.gnome.shell.extensions.paperwm` (reported 2026-11-07): commit `f0c9242` added the `remember-window-sizes` and `window-sizes` keys to `schemas/org.gnome.shell.extensions.paperwm.gschema.xml` but did not commit the regenerated `schemas/gschemas.compiled`. The extension is installed as a symlink to the repo, so the shell loaded the stale compiled schema and `extension.getSettings()` threw when `settings.js` read the new key. Fix: `make -C schemas gschemas.compiled` (verify with `gsettings --schemadir schemas list-keys org.gnome.shell.extensions.paperwm | grep remember`), then restart the shell (logout/login; Alt-F2 `r` is X11-only) because GSettings caches the compiled schema per process. Commit the binary alongside every schema edit — the `4476975`/`83e5f75` commits did.
